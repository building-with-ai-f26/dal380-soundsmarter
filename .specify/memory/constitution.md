# SoundSmarter Constitution

## Core Principles

### I. HANDOFF.md Is Authoritative

`HANDOFF.md` is the single source of truth for product decisions. Specs, plans, tasks,
and code MUST conform to it. The agent MUST NOT change, reinterpret, or work around a
product decision on its own; anything that needs deciding goes under "Questions for design"
in `HANDOFF.md`. If a spec or plan conflicts with `HANDOFF.md`, `HANDOFF.md` wins.

Rationale: product decisions are made in design review and by the owner; the agent builds.

### II. One Build at a Time

Work MUST stay inside the current build's scope as defined in the `HANDOFF.md` roadmap.
Features scheduled for a later build MUST NOT be pulled forward, even partially, without
an owner decision recorded in `HANDOFF.md`. If a task grows big or unclear, stop and
propose a smaller working slice.

Rationale: each build has a weekly deadline; scope creep is the main schedule risk.

### III. Numbers Come from Code

Every metric shown to the user (filler counts, rates, pauses, prep time, and so on) MUST be
computed deterministically in code from transcript and audio data, never generated by an LLM.
LLMs MAY classify (e.g. lexical fillers) and narrate (e.g. recommendations) on top of
computed numbers. Metric definitions follow the Metrics spec in `HANDOFF.md`.

Rationale: users track improvement over time; numbers must be reproducible and plottable.

### IV. Review Before Every Commit

Before any commit, the agent MUST show the owner what will be committed and get approval,
even when told "commit it." Owner-written or owner-directed text: show the exact diff.
Generated or bulk files: a file list plus summary, flagging changes to existing files,
secrets, or public-facing text.

Rationale: the owner is accountable for the repo and is learning the workflow.

### V. No Secrets in Code

API keys, tokens, and credentials MUST be read from environment variables (`.env`, which
is git-ignored) and MUST NEVER be hardcoded, committed, printed, or logged. Every new
variable MUST be added to `.env.example` with a placeholder value.

Rationale: leaked keys cost money and must be rotated; prevention is cheaper.

## Technical Constraints

- Build 1 is a throwaway local prototype; disposable code is acceptable. From Build 2 the
  lean stack is a web client, Python backend, and SQLite (see `HANDOFF.md` → Technical
  choices); it is a lean, not a lock.
- Before writing any provider call (speech-to-text, LLM), confirm flag names and model
  support against the provider's current docs.
- Avoid unnecessary abstractions and dependencies; the owner must be able to understand
  the main components.

## Development Workflow

- Plan before coding: propose a brief plan and get approval before touching multiple files.
- Small batches: each change is reviewable and explainable in a single pull request.
- Branches and commits: one branch per build (e.g. `build-1-prototype`), merged to `main`
  via pull request; Conventional Commits; tag each submitted build (`build-1`, ...).
- Verify: run relevant checks and the app before saying "done," and state how it was verified.
- Stop when looping: if a fix fails twice in a row, stop, summarize, and ask.
- Keep `docs/index.html` (PRD + build log) current for each weekly build.

## Governance

This constitution governs spec-kit work in this repo. `HANDOFF.md` governs product decisions;
`AGENTS.md` governs day-to-day agent operations. Where they overlap, `HANDOFF.md` wins on product
and `AGENTS.md` and this constitution must be kept consistent.

Amendments require owner approval and a commit following Principle IV. Versioning follows
semantic versioning: MAJOR for removed or redefined principles, MINOR for added or materially
expanded principles or sections, PATCH for wording fixes. Every spec, plan, and pull request
SHOULD be checked against these principles.
